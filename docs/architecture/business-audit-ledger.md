# Journal d'audit métier

La migration `20261106130000_business_audit_ledger` crée `audit.evenement_metier` dans un schéma PostgreSQL distinct. Le périmètre des 18 tables métier dans `public` reste inchangé.

Chaque événement porte un horodatage serveur, un ordre d'insertion monotone `event_sequence`, un acteur métier (nul pour les traitements système), un code d'action, une entité cible et son identifiant, ainsi que le dossier auquel l'événement appartenait au moment de l'action. `event_sequence` départage les événements dont l'horodatage est identique et fournit un ordre stable pour la chronologie. La migration `20261109110000_backfill_business_audit_event_sequence_order` réattribue les valeurs des événements déjà présents selon `occurred_at`, puis `id`, avant de repositionner la séquence pour les nouvelles écritures. Si plusieurs événements historiques partagent exactement le même horodatage, leur ordre causal initial n'est pas reconstructible à partir des données conservées. Le motif optionnel est stocké séparément dans `reason` et limité à 500 caractères ; il est réservé aux justifications métier explicites. Le `dossier_id` est volontairement une valeur historique sans clé étrangère : un événement reste consultable même si le signalement est ensuite détaché ou si une entité est archivée.

Tous les événements de statut historiques sont copiés pendant la migration, y compris ceux des signalements sans dossier. L'identifiant de la ligne d'historique legacy est conservé comme référence source. Lorsqu'un signalement est associé à un dossier, ses événements antérieurs sans dossier sont recopiés dans la chronologie de ce dossier avec une référence à l'événement source. Les lignes sources restent inchangées ; un index unique empêche les doublons pour un même dossier. Les associations déjà supprimées avant cette migration ne peuvent pas être reconstituées avec certitude.

L'API écrit les événements via `recordBusinessEvent(tx, event)` à l'intérieur de la transaction métier. Les métadonnées sont limitées à une allowlist de clés et à des valeurs scalaires bornées. Les changements de priorité conservent `previousPriority` et `nextPriority`. Les changements de localisation conservent les coordonnées, la précision et le libellé de localisation avant/après (`previous*` / `next*`) afin de reconstituer les valeurs métier modifiées ; ces libellés sont limités à 1 000 caractères. Ne pas y inscrire de compte rendu, adresse e-mail, téléphone, jeton, URL signée, contenu de fichier ou autre donnée personnelle/secrète sans décision de gouvernance explicite.

Le provisionnement initial d'un compte citoyen et les modifications de profil sont aussi journalisés dans la transaction qui écrit le compte. Les événements `COMPTE_CREE` et `COMPTE_PROFIL_MODIFIE` ne copient aucun nom, e-mail, téléphone ni contenu de profil dans les métadonnées. L'attribution automatique du rôle `CITOYEN` est enregistrée dans la même transaction.

Le périmètre couvre les transitions des signalements, les dossiers, affectations, interventions, vérifications, rôles, les modifications de référentiels/types de déchets, équipes, appartenances et compétences, ainsi que l'ajout et la purge des médias privés. Les chemins de stockage et contenus de fichiers ne sont jamais inclus. La migration `20261106140000_business_audit_referential_targets` étend le contrôle des entités autorisées à ces cibles métier et fixe le `search_path` de la fonction trigger à `pg_catalog` pour éviter toute résolution d'objet dans un schéma mutable.

RLS est activé sans policy d'accès direct ; les privilèges de `PUBLIC`, `anon`, `authenticated` et `service_role` sont révoqués. Des triggers interdisent les UPDATE, DELETE et TRUNCATE ordinaires. Le rôle PostgreSQL utilisé par l'API doit être le rôle serveur autorisé à écrire via Prisma, jamais un rôle Data API client. Comme pour toute protection dans PostgreSQL, un propriétaire de table ou superutilisateur peut désactiver un trigger ou modifier les privilèges : une garantie face à un DBA compromis nécessite un rôle runtime dédié et distinct du propriétaire/migrateur, à configurer explicitement avant d'affirmer une immutabilité administrateur-proof.

La route `GET /api/v1/cases/:idDossier/history` lit la chronologie audit du dossier, avec les anciens événements backfillés. L'accès reste soumis au rôle `RESPONSABLE_TRAITEMENT`.
